## 设计理念

PrismTrans 的核心灵感来自光学棱镜——当一束白光穿过棱镜，它被分解为多彩光谱；当一段原文进入 PrismTrans，它被**六条独立智能体路径**同时解析、重构、裁决，最终折射出一道精准、地道、风格完整的译文之光。

传统翻译工具只有"一对一"的映射逻辑。PrismTrans 构建了一个**微型翻译议会**：六位专家同时翻译、互相批判、择优融合，让译文质量不再依赖单一模型的运气。

---

## 六路智能体架构

| 路径 | 角色 | 核心使命 | 视角 |
|:----:|:-----|:---------|:-----|
| **A** | 语言学家 | 忠实 | 逐句对应，严格保留原文语义与结构 |
| **B** | 本土编辑 | 地道 | 以母语者视角自然重构表达 |
| **C** | 领域专家 | 精准 | 识别领域术语，确保专业准确性 |
| **D** | 动态智能体 | 自适应 | **根据文本特征实时生成**的补位专家 |
| **E** | 隐语诏释者 | 解码 | 诊断言外之意、潜台词、情感暗示 |
| **F** | 风格镜像师 | 文体 | 还原作者的声音与修辞等效迁移 |

### 第四智能体的诞生

D 路是 PrismTrans 的**独特设计**。在每次翻译开始前，系统会分析待译文本的主题、领域、风格，动态生成一个专门为此文本量身定制的第四个智能体——可能是"法律合规顾问"、"技术文档架构师"或"文学意象重构师"。这不是预设模板，而是真正的实时角色创造。

## 工作流程

```
  原文输入
      |
      v
+---------------------------------------------------+
|  Step 0: 动态智能体生成 (Meta Agent)              |
|         分析文本 → 创造专属 D 路角色              |
+---------------------------------------------------+
      |
      v
+---------------------------------------------------+
|  Step 1: 五路并发独立翻译 (A/B/C/D/F)             |
|         五种视角同时输出完整译文草稿               |
|         流式实时展示各路进度                       |
+---------------------------------------------------+
      |
      v
+---------------------------------------------------+
|  Step 2: 隐义后处理 (E)                           |
|         诊断言外之意、潜台词、文化暗示              |
|         + 交叉批判网络 (5路互审)                   |
|         每条路接受其他两路的批判性审查              |
+---------------------------------------------------+
      |
      v
+---------------------------------------------------+
|  Step 3: 综合裁决 (Synthesis)                     |
|         评估五路质量 → 动态选择主轴                |
|         融合各路优势 → 采纳批判建议                |
|         隐义落地 → 最终裁决译文                    |
+---------------------------------------------------+
      |
      v
+---------------------------------------------------+
|  Step 4: 质量终审 (Audit)                         |
|         忠实度 / 流畅度 / 地道度 三维评分          |
|         评语分析亮点与不足                         |
+---------------------------------------------------+
      |
      v
  迭代优化 (多轮模式)
```

### 迭代机制

每一轮迭代都基于上一轮的完整记忆：
- **备忘录**：记录遗留问题、待优化片段、下轮策略
- **批判反馈**：各路收到针对自己的批评，逐条修复
- **早期预览**：第一轮即展示初步草稿，无需等待全程

## 五大自适应模式

系统根据文本长度智能选择最优翻译策略：

| 模式 | 触发条件 | 轮次 | 隐义 | 批判 | 适用场景 |
|:----:|:---------|:----:|:----:|:----:|:---------|
| **精炼** | < 500 字 | 用户设定 | 有 | 有 | 短句、金句、诗词 |
| **标准** | < 2,000 字 | 最多 2 轮 | 有 | 有 | 日常文档、邮件 |
| **效率** | < 5,000 字 | 1 轮 | 有 | 无 | 长文快速翻译 |
| **轻量** | < 12,000 字 | 1 轮 | 无 | 无 | 超长文档轻量处理 |
| **分块** | > 12,000 字 | 逐块裁决 | 无 | 无 | 书籍、论文、报告 |

分块模式采用**串行递进+上下文记忆**：每一块翻译都携带前一块的上下文，确保长文连贯不脱节。

采用**暖石主题 (Warm Stone)** 设计语言：

## 快速开始

1. 克隆仓库
2. **启动本地服务器**（ES modules 需要 HTTP 协议）：

   ```bash
   python -m http.server 8000
   # 或使用 Node.js: npx serve .
   # 或 VS Code Live Server
   ```

3. 打开浏览器访问 `http://localhost:8000`
4. 点击右下角 **设置** → 填入你的 API 密钥
5. 选择源语言和目标语言
6. 粘贴文本或拖拽上传文件
7. 点击 **启动翻译引擎**

> **为什么要启动服务器？** PrismTrans Pro V6 已升级为 ES Modules 架构（`<script type="module">`），现代浏览器出于安全策略禁止 `file://` 协议加载模块文件，必须通过 HTTP 协议访问。

> **API 选型建议**：Gemini Flash 系列提供充足免费额度，适合入门体验；DeepSeek 性价比最优，深度思考模式可控；Claude Sonnet 长文本专注能力顶尖；GPT 4.1 系列超长上下文无出其右。

## 技术栈

- **纯前端架构**：Vanilla HTML / CSS / JavaScript (ES Modules)，零构建工具
- **JS 模块化**：15 个职责单一的 ES Module（状态管理、UI 事件、翻译编排、Provider 抽象、提示词系统、文件解析、导出引擎等）
  - `translation.js` 主入口 → 拆分为 5 子模块（工具函数、DOM 辅助、阶段执行、分块流程、编排入口）
- **CSS 模块化**：16 个功能域 CSS 文件，通过 `@layer` 显式控制层叠优先级
  - 设计令牌 → 基础 → 布局 → 组件 → 动画 → 覆写，六层有序级联
  - 组件级响应式设计，每个 CSS 模块自包含
- **零运行时依赖**：无需 npm install，无需构建工具，纯浏览器原生
- **流式 API**：Fetch + ReadableStream 实现流式逐词渲染
- **多 Provider 抽象层**：统一接口对接 DeepSeek / Gemini / OpenAI / Claude 等 LLM API
- **动态智能体**：Meta Agent 实时分析文本特征，动态生成专属翻译角色
- **本地持久化**：localStorage 保存设置、密钥、历史记录、术语表
- **精致动画系统**：25+ 项 CSS 微交互动画（`cubic-bezier` 缓动、Staggered 入场、Skeleton 骨架屏）
- **错误处理**：HTTP 状态码细分提示（401/402/403/429/500/503）+ AbortController 安全中断

## 质量评审维度

每次翻译完成后，系统从三个维度给出 0-10 分评分：

- **忠实度** — 是否完整准确传达全部显性信息
- **流畅度** — 是否自然流畅，无生硬语句
- **地道度** — 是否地道无翻译腔，隐含语义是否等效呈现

评分不足 9 分的维度会在徽章中高亮提醒，评语明确指出改进方向。

## 项目哲学

> "翻译的本质不是语言的转换，而是意义的重构。"

### 棱镜之喻

PrismTrans 的名字源于一个物理事实：**白光穿过棱镜，不是被过滤，而是被解构**——每一束折射出的色光都携带了原始能量的一个维度，而人的眼睛只有在它们重新融合时，才能看见完整的色彩。

我们的翻译引擎遵循同样的逻辑。一段原文就像一束白光，单一的翻译路径只能捕捉它的一部分频谱。六路并行不是炫技，而是承认：**好的翻译本身就是多个维度的妥协艺术。**

### 翻译需要议会，而非独裁

语言学家守护语义的精确，本土编辑捍卫表达的自然，领域专家确保术语的权威，风格镜像师追溯作者的声音，隐义诏释者打捞字面之下的潜流——每条路径都不完美，但当它们互相审视、批评、修正时，*集体智慧超越了任何单一模型的局限。* 我们没有选择更大、更贵的模型，而是选择让多个"不够完美"的声音彼此校准。这是一个架构层面的哲学选择。

### 每一次翻译，都应该被量身定制

D 路智能体不是预设的模板。每次翻译开始前，系统会分析你的文本——它是法律合同还是抒情散文？是技术手册还是哲学论文？——然后实时生成一个为此文本定做的专属译者。这意味着**第八千次翻译和第一次，同样认真。**

### 迭代，而非一次性输出

初稿几乎总是可以更好的。PrismTrans 不满足于一次性输出，而是通过多轮迭代，每轮都带着上一轮的备忘录和批判反馈，逐轮逼近最优解。备忘录中的"遗留问题、待优化片段、下轮策略"形成了一个完整的反思回路。这是一种**认知论上的谦逊**：承认第一稿不够好，然后去改进它。

### 隐义，是翻译的真正战场

字面翻译只是基本功。真正的翻译挑战在于那些未被言说的部分——文化预设、情感底色、反讽与暗示、作者故意留下的空白。E 路隐义诏释者的存在，标志着我们对翻译的理解：**最精彩的内容，往往写在字与字之间。**

### 代码架构，亦是哲学的表达

我们没有使用框架，不是因为固执，而是因为**每个模块的边界本身就是一种设计声明**。
- 翻译引擎、Provider 抽象、提示词系统被分离为独立的模块——**职责的清晰独立**
- CSS 采用 `@layer` 分层架构，从设计令牌到动画覆盖，严格有序——**视觉系统的工程化**
- 所有模块通过 ES Module 原生互联，无构建工具、无运行时依赖——**纯粹与透明**

PrismTrans 证明了：**即便在最传统的 Web 技术栈中，也能构建出架构优雅、体验精致的应用。**
